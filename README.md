# github-hosts

定时探测 GitHub 边缘 IP，把**已验证可用**的结果写入本地 `hosts.txt`，HTTP 接口直接读取该文件返回。Rust 实现，单容器运行。

## 工作原理

```
探测（每 900 秒）→ 验证内容 → 原子写入 data/hosts.txt + data/snapshot.json
                                        ↓
                              GET /hosts 直接读文件返回
```

三个关键性质：

1. **接口读文件，不读内存。** `GET /hosts` 返回的就是磁盘上的 `hosts.txt`，逐字节一致。你可以把它当普通文件同步、备份、或用任何工具检查。
2. **原子写入。** 先写 `.tmp` 再 rename，读取方永远看到完整的旧文件或完整的新文件，不会读到半截内容。
3. **重启即用。** 启动时回读 `snapshot.json`，重启后 `/hosts` 立刻可用，不用等第一轮探测跑完。

访问频率有硬下限：`INTERVAL_SECS` 低于 600 会被**钳制到 600**，防止配置笔误把服务变成请求洪水。默认 900 秒，并在调度中加 ±10% 抖动，避免多实例同时开火。

## 先说实测结论

这台机器上连续观测到的情况（不是推测）：

| 时刻 | github.com 状况 |
|---|---|
| 17:03 | `20.27.177.113` 200 / 364ms，其余候选多数超时 |
| 17:09 | `20.205.243.166`（系统 DNS 最常返回的那个）**超时黑洞**，`140.82.121.3` 可用 |
| 17:17 | `20.205.243.166` 又恢复 200 / 470ms |
| 17:23 | github.com 整组被断（6 个 IP 全部 `000`），`raw.githubusercontent.com` 的 185.199.x 同时在线 |

而 `raw.githubusercontent.com` 的四个 Fastly 分片是**分钟级轮换**的：一分钟前只有 `185.199.109.133` 通，几分钟后只有 `185.199.110.133` 通。

这就是"有时能打开有时打不开"的根因：系统 DNS 在多个边缘之间轮询返回，而任何一个边缘在任何时刻都可能被单独黑洞，你拿到哪个全凭运气。

| 失败发生在哪一层 | 判断依据 | 能否用 hosts 解决 |
|---|---|---|
| DNS 污染 | 解析出 `46.82.174.68`、`2001::1`、`0.0.0.0` | **能**（gist 是这种，但同时被 SNI 阻断，见下） |
| IP:443 黑洞 | TCP 握手超时，但 ICMP 通、同网段邻居的 443 通 | **能**，换 IP 即可 |
| TLS SNI 阻断 | TCP 通、握手即 RST | **不能**，换 IP 无效 |
| 传输期干扰 | 握手成功、响应中途断开（curl 报 `000` 但 `tls` 有值） | 部分能 |

`gist.github.com` 实测属于第二+第三类叠加：DNS 被污染，且换个好 IP 后 TLS 握手仍被阻断（连 `openssl s_client` 都握不上）。本工具会如实把它标为 `unverified`，而不是发一个假的 IP。

## 为什么必须验证内容，而不是"这个 IP 通不通"

第一版只做 TCP/TLS 探测，结果把返回 `400 Bad Request` 的 API-only 节点排到了最前面（它比真正能服务网页的节点还快），导致 github.com 明明有 7 个可用 IP 却判失败。所以现在每个域名必须通过**真实内容**校验：

| 验证项 | 判据 | 对应的用户体验 |
|---|---|---|
| `github.com/` | HTTP 200 + 真实 HTML（含 `<html`、`github`、≥3KB） | 页面能打开 |
| `github.githubassets.com` | 200 + css/js/图片 content-type | 页面不是白底无样式 |
| 页面里真实引用的 css/js | 从首页 HTML 里抓出资产 URL 再取一次 | 样式和脚本真的能加载 |
| `raw.githubusercontent.com` | 200 + 精确文件内容（`Hello World`） | Raw 与下载按钮可用 |
| `avatars.githubusercontent.com` | 200 + PNG/JPEG 魔数 | 头像显示 |
| `codeload.github.com` | 完整 tar.gz → gunzip → tar 解析 → 成员数 ≥1 | "Download ZIP" 可用 |
| `release-assets.githubusercontent.com` | 真实 release asset 经 302 签名地址下载并校验内容 | release 附件下载可用 |
| `api.github.com/zen` | 200 + 非空 JSON | API 调用正常 |
| `github.com/...info/refs?service=git-upload-pack` | 真实的 upload-pack advertisement（约 265KB，用加长超时） | `git clone/pull` 可用 |
| objects / media / camo / user-images | 任一 HTTP 响应（真实取内容需签名 URL） | 制品、LFS、README 图片 |

两个实测踩过的坑，代码里都留了注释：

- **`codeload` 的 301 不是成功。** 很多边缘对 `tar.gz` 回 `301` 到 `https://github.com/<repo>/tar.gz/...`，而那个地址实测是 **404**。把 301 当通过会给出一个"下载 ZIP 必然失败"的 IP。
- **每个域名自己的 DNS 答案优先验证。** `codeload` 的真实边缘是 `20.205.243.165`，它**不在**官方 `/32` 名单里，按 `github.com` 的延迟排名永远排不进候选，导致"下载 ZIP"总也通不过。

## 快速开始

```bash
cd github-hosts
docker compose up -d
curl -s http://127.0.0.1:8080/hosts
```

> **Podman on Windows**：`-p 8080:8080` 只绑在 WSL 虚拟机的地址上，`127.0.0.1:8080` 连不上。用 `podman machine ssh "ip -4 addr show eth0"` 拿到 VM IP 后访问。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 状态页：浏览器得 HTML，`curl` 得纯文本（30 秒自动刷新） |
| GET | `/hosts` | **直接读 `hosts.txt` 文件返回**，带 `ETag`，支持 `If-None-Match` → 304 |
| GET | `/hosts?mode=auto` | 只固定"系统 DNS 给的 IP 与实际验证不符"的域名（从 JSON 现渲染） |
| GET | `/hosts?families=web,raw` | 只要指定分组（web / api / raw / assets / pages） |
| GET | `/v1/snapshot` | 完整探测详情 JSON（读 `snapshot.json`） |
| POST | `/v1/refresh` | 立即触发一轮探测，返回 202 |
| GET | `/healthz` | 数据质量：必需项或 git 未通过时返回 503 |
| GET | `/livez` | 存活检查，只要进程在服务就 200（容器 HEALTHCHECK 用这个） |

设计上的三个承诺：

1. **不下发空文件。** 没有可用结果时返回 503，而不是一个只有头注释的 hosts。
2. **不下发降级文件。** 新一轮覆盖数少于当前结果时保留旧文件（`is_at_least_as_good`）。
3. **不抖动。** 上一轮选中的 IP 只要还活着就继续用（粘性），即使有更快的也不换 —— 换 IP 会打断在途连接。

## 落盘文件

| 路径 | 内容 |
|---|---|
| `${STATE_DIR}/commit.json` | **提交点**：记录本轮 cycle、渲染 mode、`hosts.txt` 的哈希 |
| `${STATE_DIR}/hosts.txt` | 渲染好的 block，`/hosts` 直接返回它 |
| `${STATE_DIR}/snapshot.json` | 结构化结果，用于派生视图、状态页、重启恢复 |

`STATE_DIR` 默认 `data`（容器内 `/data`）。容器里挂了 named volume，重建容器不会丢；不挂卷每次重建都要冷启动等一轮。

### 为什么多了一个 commit.json

两个文件无法原子地一起替换。先后写会留下一个窗口：`hosts.txt` 已是新 cycle 而 `snapshot.json` 还是旧的（或反之），此时 `/hosts` 和 `/v1/snapshot` 会给出**不同的答案**；若第二次写失败，这个不一致会一直持续到下一轮成功。

所以数据文件先写、`commit.json` 最后写。它记录 cycle、mode 和 `hosts.txt` 的哈希，读取方只信任与它一致的数据文件：

- `/hosts` 与 `/v1/snapshot` 都由同一个 `authoritative()` 决策，**不可能互相矛盾**
- `hosts.txt` 被外部改动（哈希不符）→ 判定磁盘状态失效，改用内存版本
- `snapshot.json` 的 cycle 与 commit 不符 → 同样拒绝

实测：手工往 `hosts.txt` 追加一行，接口仍返回 19 行未篡改内容，并打出 `hosts.txt does not match commit.json (cycle 1); treating disk state as stale`。

### 落盘失败为什么安全

因为 commit 是提交点，写失败时旧 commit 仍在，而内存里持有更新的好结果。`authoritative()` 见到 `persisted == false` 就直接用内存，不读盘——这正是"只读卷仍能继续服务"的实现方式（旧版本号称如此，实际却优先读盘，等于没用上内存回退）。

- 单文件写入是原子的：`.tmp`（带 pid 防多实例互踩）+ rename + `sync_all`
- Unix 上 rename 后额外 fsync 父目录，否则掉电可能丢失已报告的 rename
- 文件损坏不会导致启动失败，只会忽略并重新探测

## 配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `8080` | 监听端口 |
| `INTERVAL_SECS` | `900` | 探测间隔，**低于 600 会被钳制到 600** |
| `STATE_DIR` | `data` / `/data` | 落盘目录 |
| `PROBE_TIMEOUT_SECS` | `6` | 单次连接超时。短一点，让黑洞 IP 尽快被放弃 |
| `CONCURRENCY` | `12` | 并发探测数 |
| `MAX_SCAN` | `40` | 每个分组最多筛多少个候选 IP |
| `TOP_K` | `12` | 每个域名最多验证几个候选 |
| `REPEATS` | `2` | 传输失败的重试次数（内容不符不重试） |
| `FAMILIES` | 全部 | 只探测指定分组，如 `web,raw` |
| `HOSTS_MODE` | `pin` | 默认输出模式 |
| `RUST_LOG` | `info` | 日志级别 |

## 不使用 Docker

```bash
cargo build --release
./target/release/github-hosts --once     # 探测一次、落盘、打印后退出（日志走 stderr）
./target/release/github-hosts            # 常驻 + HTTP 接口
```

`--once` 适合放进计划任务，自己写文件。

## 局限

- hosts 一个域名只能映射一个 IP。封禁轮换时最多有一个探测间隔的延迟。
- `gist.github.com`、以及所有 SNI 层被阻断的域名，换 IP 无效，工具会标 `unverified`。
- 部分 Azure 边缘（`48.202.x`、`20.175.x` 等）出现在官方 `web` 名单里，但对 `codeload` 只回 301，会被正确拒绝。
- 某分组整体被封锁时，一轮探测会拉长到 80 秒左右（每个候选都要吃满超时），由每域名 25 秒预算兜住。
